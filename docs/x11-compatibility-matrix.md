# Sophia X11 Compatibility Matrix

**Role:** current native-X compatibility evidence and admission record.

This matrix is the admission record for the **Sophia X Server Frontend**. It
answers a deliberately narrow question: which real X11 client behavior has a
reproducible, bounded proof through Sophia's own X11 server frontend?

It is not an Xorg/XLibre conformance claim. A `proven` entry means the listed
probe completes its defined proof window with `first_error=none`; it does not
imply that nearby X11 requests, extensions, window-manager conventions, or
unlisted application modes work. `startup only` means the application reaches
the stated protocol stage without a client-visible X error but has no rendered
desktop proof yet.

The native frontend is always the subject of this matrix. XLibre is a retired
prototype and deferred possible provider; its behavior cannot promote an entry
here.

## Evidence Levels

| Level | Meaning |
| --- | --- |
| `wire` | Deterministic decoder/dispatcher fixture proves one bounded X11 request, reply, event, or error shape. |
| `client` | A real client completes its bounded protocol proof with `first_error=none`. |
| `engine` | The real client produces a reduced Sophia transaction that commits through Engine state. |
| `hardware` | A bounded one-client proof reaches Engine-owned native presentation and physical input, but does not yet meet the full session-promotion gate. |
| `session` | The client reaches normal startup, routed input, resize, presentation, and teardown backed by Sophia Engine and KMS. |

The paired Milestone 3 two-xterm entry meets the complete CPU-backed `session`
promotion gate under both classic-shared and fresh confined profiles. It is the
current baseline for physical input, Engine-derived output, RandR updates,
configure-plus-pixels resize, KMS presentation, and teardown. Other entries
retain only their listed evidence level. In particular, standard DRI3/Present
`vkcube` transport is `engine` evidence until the imported Vulkan pixels pass
mixed composition, page-flip-driven feedback, and the full session gate.

gradients, and the Pad and Reflect repeat modes a gradient needs past its
ends. Gradients are evaluated per pixel rather than through a ramp table,
which on a CPU costs about the same and is exact at every scale; stops
interpolate in straight alpha and premultiply afterwards, because
interpolating premultiplied stops darkens every fade to transparent. Three

Refusals are two-tier and each names its minor: a request defined within 0.10 and not implemented answers `BadImplementation` -- the five Xorg itself never wrote (`QueryDithers`, `Scale`, `ColorTrapezoids`, `ColorTriangles`, `AddGlyphsFromPicture`), plus the three named above -- while anything above 0.10 answers `BadRequest`, because a real server of that version had no dispatch entry for it. Operators 0-13 are implemented; the Disjoint, Conjoint and PDF ranges answer `BadImplementation` and values no version defines get the extension's own PictOp error. Alpha maps and pixmap clip masks are declined rather than ignored, since ignoring one changes what the client drew without saying so. Component-alpha masks are implemented rather than approximated: Xft under LCD filtering sends them, and treating one as a plain mask renders text with colour fringes that read as a display fault. Two honest limits: RENDER results have no journal representation, so a window they touch falls back to scaling its 1x raster on non-1x displays; and a depth-32 window drawn this way still ships to the compositor tagged `XR24`, the same degradation core drawing already has. `x-authority-xterm-render-smoke` is retained as regression evidence and still reports `ascii_marker_match=true` with `first_error=none` -- it launches with a core `-fn 6x13` font, so advertising RENDER does not divert its text path. ARGB cursors (minor 27) are **stored, not yet displayed**: `CreateCursor` keeps the picture's premultiplied pixels and hotspot, clamping each channel to its alpha at ingest so a stored image always satisfies the engine's `CursorAsset` validator, and `FreeCursor` releases them -- the smoke creates and frees one over a real connection. The cursor the compositor actually draws still comes from configuration through `resolve_cursor_theme`; the authority-to-engine-to-session plumbing that would put a client's cursor on screen is a named follow-up and is not claimed here. Oversize cursors are refused rather than scaled, because a silently resized cursor is one whose hotspot no longer points where the client put it. |

Refused and why: 1 `ChangeSaveSet` (no save-set substrate, and without reparenting it has nothing to do); 3, 4 and 23 to 27 (cursor requests, blocked on the same authority-to-engine cursor plumbing RENDER's stored ARGB cursors name as a follow-up); 20 to 22 (installing a region as a clip or shape remains unimplemented; core clip origins are now preserved, removing the earlier minor-20 prerequisite gap); 29 to 32 (cursor presentation and pointer constraint, both across the engine boundary); 33 and 34 (session shutdown authority, deliberately owned elsewhere). Two defects this fixed, both previously untested: `FetchRegion` wrote a count at bytes 8..10 and extents from 16, where the protocol puts extents at 8..16 with no count, so a real client read `extents.x` as a rectangle count and zeros for the rest; and `QueryVersion` answered a hardcoded 6.0 without clamping to what the client asked for. A third was caught before it shipped and is now guarded by a sweep across the whole minor range: minors 20 to 22 briefly had decoders with no dispatcher behind them, which decodes a request past every family matcher into a fallthrough that panics -- any unprivileged client could have taken the server down with one. A minor is decoded only once something answers it. Two honest limits: minor 2 `SelectSelectionInput` is accepted and validated but no `XFixesSelectionNotify` has ever been encoded, so clients believe they subscribed to selection changes they will not be told about; and the `x-authority-zenity-smoke` and `x-authority-gtk3-smoke` traces are **not** XFIXES evidence -- both report `first_error=none` but neither reaches opcode 138 offline, because with no window manager nothing is admitted and GTK never gets far enough to compute a region. |

## Admission Rule

Every native X11 change must update this matrix when it changes a real-client
result. The change should include:

1. The exact client, command, environment precondition, and version if it
   affects request behavior.
2. The first missing request, reply, event, or extension fact, captured in
   bounded trace data without publishing client metadata or payloads.
3. A focused wire/authority regression plus the corresponding real-client
   command. The client output must retain `first_error=none`.
4. The smallest matrix row or row update that states both what is proven and
   what is deliberately not proven.

An unsupported request must remain a normal client-visible X11 error. Do not
advertise an extension merely to advance a probe, add unrelated Xorg behavior
speculatively, or route raw X11 state into Sophia Engine.

## Promotion Gate

An application class can move from `engine` to `session` evidence only when a
real client proves all of the following through the native frontend:

- normal startup and teardown;
- configured size and output facts derived from Engine rather than fixed setup
  constants;
- Engine-selected keyboard and pointer delivery, including the applicable X11
  focus/grab semantics;
- buffer readiness, delayed release, and presentation feedback on the chosen
  SHM or DRI3/Present path;
- committed Sophia Engine state and real KMS presentation; and
- the applicable classic shared-X or confined-namespace policy.

Until then, unsupported applications remain unsupported by the native session.
Reconsider an optional XLibre provider only after measured compatibility gaps
justify its authority and maintenance cost.
